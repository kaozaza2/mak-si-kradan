# หมากสี่กระดาน

เกมกระดานออนไลน์ 2 ผู้เล่นบนกระดาน 8×8 ที่หมากทุกตัวเป็นของกลาง
ใครถึงเทิร์นก็หยิบหมากตัวไหนก็ได้ไปเล่น และคะแนนเป็นของคนที่กิน

```
เลือกหมาก → หาเส้นทางกิน → กินให้มากที่สุด → กระดานเปลี่ยน → คู่แข่งใช้กระดานต่อ
```

## Docker

วิธีที่ง่ายที่สุดคือใช้ compose ซึ่งยก Redis กับตัวเกมขึ้นมาพร้อมกันและเก็บข้อมูลลง volume

```bash
cp .env.example .env
# ใส่ AUTH_SECRET ที่ยาวและสุ่มจริง เช่น
echo "AUTH_SECRET=$(openssl rand -hex 32)" >> .env

docker compose up -d --build
# เปิด http://localhost:8090
```

เปลี่ยนพอร์ตด้วย `APP_PORT` ใน `.env` และต้องตั้ง `PUBLIC_URL` ให้ตรงกับ URL ที่ผู้ใช้
เห็นจริงเสมอ เพราะทั้งลิงก์เชิญและการ redirect ข้าม node อ้างอิงค่านี้

ไม่ตั้ง `MAIL_WEBHOOK_URL` รหัส OTP จะพิมพ์ลง log ของ container ซึ่งพอสำหรับ
การลองเล่นในเครื่อง:

```bash
docker compose logs app | grep -i "verification code"
```

หรือจะรันแบบ container เดียวโดยไม่ใช้ compose ก็ได้:

```bash
docker build -t mak-si-kradan .
docker run -d --name msk -p 3000:3000 mak-si-kradan
```

image ขนาด ~264MB บน `oven/bun:1.4-alpine` รันด้วย user `bun` (ไม่ใช่ root)
มี `HEALTHCHECK` ยิงไปที่ `/health` และรับ SIGTERM ปิดตัวเองสะอาด

runtime image ไม่มี prisma CLI ติดไปด้วย (ใหญ่กว่า 250MB โดยไม่ได้ใช้) — ตอน build
จะแปลงสคีมาเป็น `prisma/init.sql` ไว้ แล้ว entrypoint สร้างตารางเองด้วย `bun:sqlite`
ถ้ายังไม่มี ต้องใส่ `--omit=peer` ตอนติดตั้ง production ด้วย เพราะ `@prisma/client`
ประกาศ prisma CLI เป็น optional peer

เก็บฐานข้อมูลถาวรด้วย volume ที่ `/app/data` (โฟลเดอร์นี้เป็นของ user `bun` ในตัว image แล้ว):

```bash
docker run -d --name msk -p 3000:3000 \
  -e DATABASE_URL=file:/app/data/game.db \
  -v msk-data:/app/data \
  mak-si-kradan
```

ถ้า map port ไม่ตรงกับ 3000 หรืออยู่หลัง reverse proxy ต้องตั้ง `PUBLIC_URL`
ให้ตรงกับ URL ที่ผู้ใช้เห็นจริง ไม่งั้นลิงก์เชิญที่สร้างจะชี้ผิดที่:

```bash
docker run -d --name msk -p 8080:3000 \
  -e PUBLIC_URL=https://game.example.com \
  -e TURN_SECONDS=60 \
  mak-si-kradan
```

state ทั้งหมดอยู่ใน memory ของ container — รีสตาร์ตแล้วเกมที่ค้างอยู่หายหมด
และยังสเกลเป็นหลาย replica ไม่ได้ เพราะผู้เล่นสองคนต้องอยู่ process เดียวกัน

## โครงสร้าง

```
src/engine/     Game Engine ล้วน ๆ — ไม่รู้จัก HTTP/WebSocket/บัญชีผู้ใช้
  board.ts      กระดาน 8 ทิศ ช่องกลาง 4 ช่อง
  rules.ts      การกิน chain การหาเส้นทางที่กินได้มากที่สุด การเดินปกติ
  game.ts       state machine ของ match, คะแนน, ประวัติการเดิน, สถิติ
src/server/     Online layer
  hub.ts        Lobby, Quick Match, Room, Challenge, reconnect  (ไม่ผูกกับ transport)
  match.ts      game session + นาฬิกาเทิร์น + โหวตจบเกม + state hash
  protocol.ts   สัญญาข้อความระหว่าง client/server
  index.ts      Bun WebSocket + static server
public/         หน้าเว็บ (vanilla JS ไม่มี build step)
scripts/e2e.ts  ทดสอบ end-to-end ผ่าน WebSocket จริง
```

Engine ไม่ import อะไรจาก `src/server/` เลย จึงเอาไปใช้กับ AI, offline mode,
replay หรือ client อื่นได้ตรง ๆ

## บัญชีผู้ใช้และ ranking

เล่นเป็น guest ได้ทันทีเหมือนเดิม การสมัครเพิ่มให้แค่ ranking กับประวัติที่ผูกกับตัวตนถาวร

สมัครด้วย **อีเมล + รหัสผ่าน แล้วยืนยันด้วย OTP 6 หลัก** หรือ **ล็อกอินด้วย Google**
รายละเอียด endpoint ทั้งหมดอยู่ใน [docs/API.md](docs/API.md)

รหัสผ่านแฮชด้วย argon2id (`Bun.password`) และไม่เคยเก็บค่าดิบ รหัส OTP ก็เก็บแต่แฮช
ผูกกับอีเมลปลายทาง กรอกผิดได้ 5 ครั้งแล้วรหัสถูกทิ้ง ต้องขอใหม่ ขอรหัสใหม่ก็ยกเลิก
รหัสเก่าทันที การล็อกอินผิดกับไม่มีบัญชีคืนข้อความเดียวกันและใช้เวลาเท่ากัน จะได้ไม่
บอกใบ้ว่าอีเมลไหนมีบัญชีอยู่ และ `resend-otp` ตอบเหมือนกันเสมอด้วยเหตุผลเดียวกัน
มี rate limit ต่อ IP ทุก endpoint ที่เดาได้

**Google** ตรวจ ID token เองด้วยกุญแจสาธารณะของ Google (JWKS แบบแคชไว้) รับเฉพาะ
RS256 กัน alg confusion และผูกกับบัญชีเดิมที่อีเมลตรงกันก็ต่อเมื่อ Google ยืนยันอีเมล
นั้นแล้วเท่านั้น ไม่งั้นใครก็อ้างอีเมลของคนอื่นเพื่อยึดบัญชีได้

**อีเมลที่ยังไม่ยืนยันเล่นได้ทุกอย่าง** แค่แมตช์นั้นจะไม่ถูกนับ rating ซึ่งกันการสมัคร
รัว ๆ เพื่อปั่นเรตติ้งไปในตัว

**Rating เป็น Elo** ที่ขยายไปหลายคนด้วยการแตกเป็นการเจอกันทุกคู่แล้วเฉลี่ยด้วย (n-1)
K-factor ลดลงเมื่อเล่นเยอะขึ้นและเมื่อเรตติ้งสูง

จะนับคะแนนก็ต่อเมื่อ **ทุกที่นั่งเป็นบัญชีที่สมัครแล้ว** ไม่มีบอทและไม่มี guest
ไม่งั้นเก็บแต้มจากบอทได้ไม่จำกัด ส่วนที่นั่งที่ AI คุมแทนยังนับ เพราะการทิ้งเกม
เป็นความรับผิดชอบของเจ้าของที่นั่ง และคนที่ยอมแพ้ถือว่าแพ้ทุกคู่แม้คะแนนจะนำอยู่

## โหมดการเล่น

* **2–4 ผู้เล่น** — หมากเป็นของกลางอยู่แล้ว การเพิ่มผู้เล่นจึงเป็นแค่การเพิ่มคิวในลำดับเทิร์น
* **Quick Match** — จับคู่อัตโนมัติ 2 คน
* **Private Room** — เข้าด้วยรหัส 6 ตัวหรือลิงก์เชิญ ตั้งได้ 2–4 คน
* **เพิ่ม AI ในห้องได้** — เจ้าของห้องเติมบอทลงที่นั่งว่างและเอาออกได้ก่อนเริ่มเกม
  จึงเล่น 4 คนโดยมีเพื่อนแค่คนเดียวก็ได้
* **Public Room** — โผล่ในรายการห้องให้ใครก็กดเข้าได้ (รายการไม่เปิดเผยรหัสห้อง)
* **เพื่อน** — เพิ่มด้วยชื่อผู้ใช้หรืออีเมล เห็นสถานะออนไลน์ข้าม node ชวนเข้าห้องหรือท้าดวลได้จากรายชื่อ
* **Challenge** — ท้าผู้เล่นที่ว่างอยู่โดยตรง
* **เล่นกับ AI** — 3 ระดับ ง่าย / ปานกลาง / ยาก

## AI

AI อยู่ใน `src/engine/ai.ts` เป็น pure function ทั้งหมดเช่นเดียวกับส่วนอื่นของ engine
ใช้ negamax + alpha-beta บน **ผลต่างจำนวนหมากที่กิน** โดยตรง เพราะเกมนี้เป็น score war
ไม่ใช่เกมยึดพื้นที่

สิ่งที่ได้ผลจริงจากการให้บอทเล่นกันเองคือ **การประเมินภัยคุกคามที่ปลายการค้นหา**
ไม่ใช่ความลึก การเพิ่มเป็น 4 ply กลับ *แพ้* 2 ply เพราะท่าเดินเปล่ามีเป็นร้อยท่า
การตัดกิ่งให้แคบพอจะค้นลึกได้จึงมองข้ามท่าที่ปลอดภัยจริง ๆ ไป ส่วนรุ่นที่เติมค่า
"ปลายทางแล้วอีกฝ่ายยังกินต่อได้อีกเท่าไร" ชนะรุ่นที่ไม่มีถึง 11/12 เกม

| ระดับ | วิธีคิด | คิดต่อตา |
| --- | --- | --- |
| ง่าย | คว้าการกินที่ยาวที่สุดตรงหน้า 75% ของเวลา ไม่คิดต่อ | < 1ms |
| ปานกลาง | negamax 2 ply — กินได้เท่าไรลบสิ่งที่คู่แข่งกินคืนได้ | ~1ms |
| ยาก | 2 ply + ค่าภัยคุกคามที่ปลายทาง และดูท่าเดินเปล่าครบทุกท่า | ~6ms |

## AI คุมแทนเมื่อผู้เล่นหายไป

แยกให้ชัดระหว่างสองอย่างที่ต่างกันมาก:

* **ยอมแพ้** — ถอนตัวถาวร ข้ามในลำดับเทิร์น และหมดสิทธิ์ชนะ ในเกม 3–4 คนที่เหลือเล่นกันต่อ
  เกมจบเมื่อเหลือคนเดียว
* **หลุด / ออกจากเกม / ปล่อยหมดเวลา** — AI (ปานกลาง) เข้ามาคุมที่นั่งแทน คะแนนยังเป็น
  ของเจ้าของที่นั่ง และได้คุมคืนทันทีที่ reconnect หรือคลิกหมากเอง เกมจึงไม่ค้าง
  เพราะรอคนที่ไม่อยู่

ถ้าไม่มีใครเชื่อมต่ออยู่ในแมตช์เลย บอทจะหยุดเดินไว้ก่อนแทนที่จะเล่นเกมทิ้งเปล่า ๆ
แล้วเดินต่อเมื่อมีคนกลับเข้ามา

## กติกาที่ implement

* กระดาน 8×8 ช่องกลาง 4 ช่อง `(3,3) (3,4) (4,3) (4,4)` ว่างตั้งแต่เริ่ม → หมาก 60 ตัว
* หมากไม่มีเจ้าของ เลือกหมากตัวใดก็ได้ในเทิร์นของตัวเอง
* กิน = กระโดดข้ามหมาก 1 ตัวไปช่องว่างถัดไป ได้ทั้ง 8 ทิศ (`+` และ `X`)
* กินต่อเนื่องได้ เปลี่ยนทิศระหว่าง chain ได้ หมากที่ถูกกินออกจากกระดานทันที
* **Maximum Capture**: เมื่อเลือกหมากแล้ว ต้องเดินเส้นทางที่กินได้มากที่สุด*ของหมากตัวนั้น*
  (แต่จะเลือกหมากที่กินได้น้อยกว่าตัวอื่นก็ได้ — การเลือกหมากเกิดก่อนการคำนวณ)
* ถ้าหมากที่เลือกกินไม่ได้ ขยับได้ 1 ช่อง 8 ทิศ แล้วจบเทิร์น ไม่ได้คะแนน
* 1 การกิน = 1 คะแนน คนคะแนนมากกว่าตอนจบเป็นผู้ชนะ (คะแนนเท่ากันคือชนะร่วมกัน)

## สองจุดที่ต่างจาก concept เดิม และเหตุผล

**1. ช่องกลาง 4 ช่องเป็น "ช่องว่างเริ่มต้น" ไม่ใช่ "พื้นที่ว่างถาวร"**

concept เขียนว่ามีช่องวางหมาก 60 ช่องและเริ่มด้วยหมาก 60 ตัว ซึ่งแปลว่ากระดานเต็ม
ตั้งแต่เทิร์นแรก และถ้าช่องกลางลงไม่ได้ด้วย ก็จะไม่มีช่องว่างให้กระโดดลงเลย
เกมจะไม่มี legal move ตั้งแต่ต้นและจบทันที

ที่ implement คือให้ช่องกลางเป็นช่องว่างปกติที่ลงได้ ทำให้ 64 − 4 = 60 หมากลงตัวพอดี
และเปิดเกมมามีหมากให้เลือกเล่นได้ 32 ตัว (20 ตัวกินได้ / 12 ตัวขยับลงช่องกลางได้)

**2. เพิ่มเงื่อนไขจบเกม "ไม่มีการกินติดต่อกัน 20 เทิร์น"**

concept ให้เงื่อนไขจบไว้ว่า "ไม่มีการเล่นที่ถูกต้องเหลือ" แต่เพราะหมากที่กินไม่ได้
ยังขยับได้เสมอ เงื่อนไขนี้จะเป็นจริงก็ต่อเมื่อกระดานเต็ม 64 ช่อง ซึ่งเกิดขึ้นไม่ได้
เกมจึงยืดได้ไม่รู้จบถ้าไม่มีใครกดจบ

จึงเพิ่มตัวนับเทิร์นที่ไม่มีการกิน (`noCaptureLimit` ปรับได้ ค่าเริ่มต้น 20)
พอครบก็จบเกมและตัดสินด้วยคะแนน — ทำงานคู่กับ Vote to End และการยอมแพ้ที่มีอยู่แล้ว

## Online layer

* **Guest Play** — เข้ามาเล่นได้ทันที ได้ id แบบ `guest_7fa82c` และชื่อสุ่ม ตั้งชื่อเองได้
* **Quick Match** — เข้าคิวจับคู่อัตโนมัติ
* **Private / Public Room** — รหัส 6 ตัวอักษร + ลิงก์เชิญ `/join/K4D8Q2` และรายการห้อง public
* **เพื่อน** — เพิ่มด้วยชื่อผู้ใช้หรืออีเมล เห็นสถานะออนไลน์ข้าม node ชวนเข้าห้องหรือท้าดวลได้จากรายชื่อ
* **Challenge** — ท้าผู้เล่นที่ว่างอยู่โดยตรง (`PENDING / ACCEPTED / DECLINED / EXPIRED / CANCELLED`)
* **Authoritative server** — client ส่งได้แค่เจตนา (`select` / `capture` / `move`)
  server ตรวจกติกาทั้งหมดแล้ว broadcast canonical state พร้อม `stateHash` ไว้ตรวจ desync
* **Reconnect** — session token เก็บใน localStorage หลุดแล้วต่อกลับได้ที่นั่งเดิม state เดิม
* **Turn timer** — ค่าเริ่มต้น 45 วินาที หมดเวลาแล้วระบบเล่นแทนด้วยเส้นทางที่กินได้มากที่สุด
* **Replay** — ทุกเทิร์นถูกบันทึกเป็น `MatchAction` (piece, path, captures) แสดงในหน้าสรุปผล

## Crossplay

โปรโตคอลไม่ได้ผูกกับเว็บเลย เว็บ client ใน `public/` ใช้ REST กับ WebSocket ชุดเดียว
กับที่ client อื่นจะใช้ ไม่มีทางลัดพิเศษ — เขียนแอปมือถือต่อเข้ามาได้เลย

* **เวอร์ชัน** — `GET /api/v1/config` บอก `apiVersion` กับ `protocolVersion`
  REST รับทั้ง `/api/...` และ `/api/v1/...` ส่วน WebSocket ตรวจเลขเวอร์ชันตอน `hello`
  แล้วตอบข้อความที่อ่านรู้เรื่องถ้าไม่ตรง แทนที่จะพังเงียบ ๆ ตอนผู้ใช้ยังไม่อัปเดตแอป
* **CORS** เปิดให้ตั้งค่าได้ และใช้ bearer token ไม่ใช่ cookie จึงไม่มีปัญหา CSRF
* **โปรโตคอลไม่มีข้อความภาษาคนอยู่ในนั้นเลย** — `error` / `info` ส่งแค่ `code` กับ `params`
  ส่วนคำแปลดึงแยกที่ `GET /api/v1/messages?locale=th` (มี th/en) client จะใช้แคตตาล็อกนี้
  หรือฝังคำแปลเองก็ได้ ทำให้แอปมือถือเลือกภาษาได้เอง เช็ค error ด้วย `code` แทนการ
  เทียบสตริง และแก้คำพูดได้โดยไม่ทำให้แอปที่ปล่อยไปแล้วพัง
* **ตัวตนแบบเดียวกันหมด** — guest กับบัญชีจริงใช้ token รูปแบบเดียวกัน
* **Google Sign-In แบบ ID token** ไม่มี redirect flow ซึ่งเป็นวิธีที่ SDK มือถือใช้อยู่แล้ว

คู่มือสำหรับคนเขียน client อยู่ที่ [docs/API.md](docs/API.md)

## รันหลาย node

หัวใจของการกระจายคือ **แมตช์หนึ่งอยู่ node เดียวเสมอ** เกมผลัดตาเป็น single-writer
อยู่แล้ว การพยายามแชร์ state ของแมตช์ข้าม node มีแต่จะเพิ่ม lock กับ race
โดยไม่ได้อะไรกลับมา สิ่งที่แชร์กันจริง ๆ ผ่าน Redis มีแค่สี่อย่าง:

1. ทะเบียนว่าห้อง/แมตช์ไหนอยู่ node ไหน — ใช้ redirect ผู้เล่นไปให้ถูกเครื่อง
2. คิวจับคู่ (ใช้ `LPOP`/`RPUSH` ซึ่ง atomic จึงไม่มีทางหยิบคนเดียวกันซ้อนกัน)
3. จำนวนคนออนไลน์รวมทุก node
4. ช่องส่งข้อความระหว่าง node

```bash
docker run -d -p 6379:6379 redis:7-alpine

AUTH_SECRET=... REDIS_URL=redis://localhost:6379   PORT=3010 NODE_ID=node-a NODE_URL=http://localhost:3010 bun start
AUTH_SECRET=... REDIS_URL=redis://localhost:6379   PORT=3011 NODE_ID=node-b NODE_URL=http://localhost:3011 bun start
```

`AUTH_SECRET` ต้องเหมือนกันทุก node เพราะ **token ของ guest ก็ถูกเซ็นเหมือนบัญชีผู้ใช้**
node ไหนก็ตรวจได้เองโดยไม่ต้องแตะฐานข้อมูลหรือแชร์ตาราง session กัน คนที่ถูก redirect
ไปอีกเครื่องจึงยังเป็นคนเดิม ชื่อเดิม ที่นั่งเดิม

ตัวอย่างสิ่งที่เกิดขึ้นเมื่อสองคนกด Quick Match คนละ node: คนที่มาทีหลังหยิบคนที่รออยู่
ออกจากคิวกลาง แล้ว node ของเขากลายเป็นเจ้าของแมตช์ อีกฝ่ายได้ข้อความ `redirect`
แล้ว client ต่อไปที่ node นั้นด้วย token เดิม เช่นเดียวกับการเข้าห้องด้วยรหัสที่
อยู่คนละเครื่อง

ไม่ตั้ง `REDIS_URL` ก็ทำงานแบบ node เดียวด้วย `LocalCluster` ที่เก็บทุกอย่างใน memory
โค้ดเส้นทางเดียวกันทั้งหมด

**ส่วนที่ scale ได้อยู่แล้ว:** REST ทั้งหมด (สมัคร ล็อกอิน อันดับ ประวัติ) เป็น stateless
ต่อฐานข้อมูลตรง ๆ เพิ่ม node ได้ทันที

**ข้อจำกัดที่ยังเหลือ:** ถ้า node ที่ถือแมตช์ล่ม แมตช์นั้นหาย (ผลที่จบแล้วยังอยู่ในฐานข้อมูล)
การกู้ต้องเขียน snapshot ของ `GameState` ลง Redis ทุกเทิร์นแล้วให้ node อื่นรับช่วง
ซึ่งโครงรองรับแล้วเพราะ `GameState` เป็น JSON ล้วนและ `Game.fromJSON` รับกลับได้
และ SQLite ต้องเปลี่ยนเป็น Postgres เมื่อมีหลาย node เขียนพร้อมกัน

## ยังไม่ได้ทำ

* แมตช์ที่กำลังเล่นอยู่ยังไม่ถูก snapshot ลง Redis จึงยังกู้ข้าม node ไม่ได้เมื่อ node ล่ม
* Spectator ตาม §19 ยังไม่ได้ทำ
* ยังไม่มีระบบจับคู่ตามเรตติ้ง (ตอนนี้ Quick Match จับใครก็ได้ที่รออยู่)
